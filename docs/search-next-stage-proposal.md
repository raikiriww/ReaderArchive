# 下一阶段搜索方案：参考主流流程后的建议

> 历史阶段记录，包含当时的方案、结果和未完成项。当前实现及最终验收以 [CPU 搜索升级](search-cpu-upgrade.md) 和 [发版验收](release-acceptance-20260905.md) 为准。

调研日期：2026-09-05。本文件是改造建议，没有实施新的搜索规则。官方方案说明其支持的做法，不保证在 Reader 收藏上的效果；以下模型及规模参数必须实测。

## 官方方案的共同做法

1. **并行查找，再合并候选。** 关键词负责标题、专有名词、原词；语义负责改写表达与概念。Elastic 推荐全文与向量组合及 RRF，Qdrant 也提供混合查找接后续排序的流程。[Elastic](https://www.elastic.co/docs/solutions/search/hybrid-search)、[Qdrant](https://qdrant.tech/documentation/tutorials-basics/reranking-hybrid-search/)
2. **对候选再次判断。** 将问题与候选文本一起交给专门的排序模型，而不只比较分别生成的向量。计算较贵，通常放在初步筛选之后。它无法找回未进入候选的文章。[Sentence Transformers](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)、[Elastic](https://www.elastic.co/docs/solutions/search/ranking/semantic-reranking)
3. **展示原句是单独步骤。** Azure AI Search 将重新排序与 captions/answers 分开，后者从原文摘取，并非凭空生成。不能把文章的最佳相似片段直接等同于用户需要的答案。[Microsoft](https://learn.microsoft.com/en-us/azure/search/semantic-search-overview)
4. **为片段保留上下文。** Anthropic 的 Contextual Retrieval 为每段补充针对该段的背景，同时用于语义与关键词查找。它区别于给每段无差别加同一篇标题。我们应先验证原有标题、章节和相邻句，再评估生成背景的额外成本。[Anthropic](https://www.anthropic.com/engineering/contextual-retrieval)

这些是多个成熟产品反复出现的模式，不意味着所有搜索服务都使用同一种模型或相同数量限制。Qdrant 的示例也展示了多向量比较等另一种后续排序方式。

## 对 Reader 的具体建议

推荐流程：**确认筛选范围 → 关键词与语义并行查找 → 合并候选并保留每篇多个片段 → 问题与原文成对比较 → 汇总文章顺序 → 选完整原句和必要上下文 → 展示与定位。**

### A. 解决目标文章提前落选

- 补齐真正的词法查找：采用成熟 BM25 实现及适合中文的分词，保留英文技术词、标识符和显式引号规则。当前 SQL 字面匹配加二字补漏不等同于 BM25。普通中文关键词路线也不能自动解决中英跨语言找回。
- 对语义模型做候选对比，至少保留现有模型作为基线；候选考虑 Qwen3-Embedding-0.6B 与 BGE-M3。评估文档与段落两个层面的查找，避免综合文章靠大量片段长期挤占名额。
- 评估不同候选预算，例如 100、200、400 个文章候选，以及每篇 2–4 个保留片段；这些是实验网格，不是行业标准或预定发布参数。不能在扩大候选后又依据原分数过早缩到 50 篇，让同一文章再次被排除。
- 用正确文章进入候选的比例先检查这一阶段，再评价后续排序。重新排序无法挽救候选中没有的目标。
- 将查询改写、翻译作为可独立对照的补充路线；本例等义英文也失败，不能默认翻译是解法。原问题必须保留，不能让生成的改写替代用户意图。

### B. 解决找对文章但选错原句

- 保存句子、段落、章节与源文字位置；根据模型的实际输入限制组合完整句子，超过预算才进一步分割。不要把整个长页面视为一个自然段。
- 每篇先保留多个可能相关片段，再用问题与原文一起判断。选择 BGE-reranker-v2-m3、Qwen3-Reranker-0.6B 等作本地候选对照；不预先宣称哪一个更好。
- 针对前列文章做更细的原句选择，必要时检查文章中其它完整段落，而非永久局限于最初最高分片段。缓存例应让篇内第二的实际答案参与最终判断。
- 以完整原句为中心补上下文；文章排序与展示原句分别验收。专门的相关性模型也不保证每句话都能回答问题，因此证据不足时明确标记，不生成不存在的答案。

### C. 部署选择

优先在现有 PostgreSQL/pgvector 上补齐上述流程，采用成熟查找和排序组件。pgvector 官方本身就介绍了结合全文查找、RRF 或 cross-encoder 的路线。[pgvector](https://github.com/pgvector/pgvector#hybrid-search)

这是基于当前仅 560 条收藏、约 8,033 个有效搜索片段，以及已有归档数据库做出的工程选择。当前没有证据表明存储引擎是这两次失败的原因。Elasticsearch 或 Qdrant 是可以对照的替代方案；更换引擎本身不会自动改正片段选择与模型判断。将来数据量、并发或索引维护成为瓶颈时再决定是否迁移。

只读检查现有服务器：Ryzen 5 7640HS、6 核/12 线程、约 60 GiB 可见内存，同时运行其它服务。本轮没有确认可用独立 GPU 推理路径，应按 CPU 路径测量。0.6B 等参数规模不能直接换算成“够快”；应测冷启动、热查询、同时归档时的响应与峰值内存。

加入文本排序模型可以先不重建现有向量；更换语义模型则必须另建版本并重算。即使新旧输出维度一样，向量也不能混用。需要保持可回退并让默认镜像包含必要组件，不能把增加 compose 配置作为启用功能的前提。

## 推荐推进方式

1. 冻结当前对照，保留两个失败例作为回归项；增加不同表达、明确原词、英文、相近干扰及无答案问题，留出一批不参与调参的验证题。
2. 在本地副本中对比三层变化：现有查找＋多片段精判；改善词法与候选范围＋精判；再加入新的语义模型。记录每层收益，避免同时更换所有环节后不知道原因。
3. 同时检查四件事：正确文章是否进入候选、前列文章是否相关、展示原句是否支持问题、实际响应是否可接受。两个已知失败必须解决，其它场景不能明显退步。
4. 根据真实资料和目标机器的结果定模型与预算，再接入正式流程。当前没有跑过这组新方案，因此不承诺准确率或耗时，也不把此前用于检查的 12 个问题当作独立准确率验证。

候选模型官方资料：[Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)、[BGE-M3](https://huggingface.co/BAAI/bge-m3)、[Qwen3-Reranker-0.6B](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)、[BGE-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3)。当前本地 fastembed 原生模型列表没有这四款，接入需要适配，不能只修改模型名称。CPU 可运行不等于实际响应达标，需按上面的目标机器测试。

目标是采用成熟的多阶段搜索方式，而非为两条问题增加特殊规则。
