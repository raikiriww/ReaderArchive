# PDF 直链归档改造计划

## 背景

Reader 当前会把所有页面结果预先命名为 `.html`，再交给 SingleFile 保存。对于直接返回 `application/pdf` 的地址，Chrome 使用内置 PDF 阅读器显示内容，但 SingleFile 只能保存阅读器外层的空页面，因此会生成一个正文为空的 HTML 存档。

已用以下地址复现：

`http://e-learning.uibe.edu.cn/meol/analytics/resPdfShow.do;jsessionid=[已隐藏]?resId=45131&lid=17417`

该地址实际返回约 543 KB、11 页的有效 PDF；现有 SingleFile 流程生成的 HTML 只有约 6.7 KB，`body` 为空。

## 目标

- 普通网页继续生成可离线打开的 HTML 存档。
- 直接返回 PDF 的地址保存原始 PDF，不生成空白 HTML。
- 判断基于浏览器实际收到的最终响应，不依赖 URL 后缀。
- 复用归档浏览器的登录状态，兼容需要登录或重定向后才能取得的 PDF。
- PDF 可以正常查看、下载、删除、重新归档，并尽可能参与正文搜索。
- 下载失败或内容无效时不得留下被标记为成功的残缺文件。
- 默认行为放进应用或镜像本身，不新增必须同步的 Compose 配置。

## 完成标准

- 示例地址归档后生成真正的 `.pdf` 文件，能打开并确认共 11 页。
- 普通 HTML 页面仍由 SingleFile 保存，结果与改动前一致。
- URL 不含 `.pdf`、经重定向到 PDF、类型声明错误但内容确为 PDF 时均可识别。
- 网站声称返回 PDF、实际返回登录页或错误页时不得误判。
- 需要登录的 PDF 使用同一浏览器会话；除任务原始地址所必需的一份记录外，会话信息不复制到文件名、额外数据库字段或错误信息。
- 中断、超时、空响应、损坏响应会失败并清理临时文件。
- “查看文件”以内联 PDF 打开，“下载文件”下载正确的 PDF。
- 重新归档可以在 HTML 与 PDF 结果之间切换，旧结果和相关索引会正确清理。
- 文字型 PDF 可进入现有搜索；无可提取文字的 PDF 仍保存成功并安全跳过正文索引。
- 现有自动检查、前端检查、容器检查全部通过。

## 实现原则

### 1. 从实际导航响应识别文件

- 不使用 URL 后缀判断。
- 不用独立的预检请求替代浏览器请求，因为这会丢失浏览器 Cookie、登录状态、一次性链接和跳转上下文。
- 在归档浏览器实际导航期间观察最终主文档响应。
- 识别 PDF 时同时参考响应类型和文件内容；内容签名是最终兜底。
- 重定向链只认最终有效响应。
- 现有复用浏览器标签页的手动登录流程也必须覆盖，不能只支持首次匿名导航。

### 2. 从同一次浏览器请求保存原始 PDF

- 扩展项目内已经维护的 SingleFile/Chrome 连接补丁或提供等价的浏览器侧捕获能力，使归档流程能够取得最终主文档的原始 PDF 字节。
- 不允许先用 SingleFile 生成空 HTML，再用一个不带浏览器登录状态的普通请求补下载。
- 捕获结果先写入归档目录中的临时文件，验证成功后再原子替换为正式文件。
- 内部文件名使用 `<task_id>.pdf`；用户可见名称继续使用安全化后的任务标题，必要时可参考服务器提供的文件名。
- 必须保留现有超时和进程终止处理，并清理所有失败产物。

### 3. 保持 HTML 流程不变

- 只有确认结果为 PDF 时才走二进制保存分支。
- 普通 HTML、需要站点规则处理的页面、手动登录后的普通页面继续走现有 SingleFile 和站点规则流程。
- 不得以“输出 HTML 很小”作为唯一判断依据。

### 4. 允许任务结果动态选择扩展名

- 任务创建时可以继续使用暂定 HTML 名称，但成功前必须把实际结果文件名更新为 `.html` 或 `.pdf`。
- 重新归档不能永久写死为 `.html`。
- 数据库现有 `output_file` 字段可以保存不同扩展名，优先不新增迁移。
- 任务只有在最终文件存在且验证通过后才可标记成功。

### 5. 正确提供文件

- 结果查看和下载接口不能固定声明为 HTML，应根据实际文件返回正确类型。
- PDF 查看使用浏览器内联阅读器，下载保留 `.pdf`。
- 通用文件列表、展示名称、大小统计、删除逻辑和结果存在性检查都必须兼容 PDF。
- 前端原则上复用现有“查看文件”和文件列表；只有确有需要时才做最小改动。

### 6. 搜索处理

- 文本提取入口应按文件类型分支。
- HTML 保持现有提取方式。
- PDF 使用轻量、可离线打包的文本提取库读取文字层。
- 没有文字层或加密且无法读取的 PDF 应标记为“无可读正文”并跳过索引，不影响归档任务成功。
- 不在本次范围内加入 OCR。

### 7. 安全与兼容性

- 对服务器建议的文件名进行清理，禁止路径穿越和特殊路径写入。
- 不在日志和用户错误信息中泄露 URL 内的 `jsessionid`、查询令牌、Cookie 或认证头。
- 限制沿用现有下载超时；对异常大文件避免整份重复复制造成不必要的内存峰值。
- 新依赖和默认行为必须进入镜像，Compose 仅作为覆盖入口；本功能不得依赖新增环境变量才能工作。

## 预计改动范围

- 浏览器归档层：捕获主文档响应，识别并返回原始 PDF。
- 任务服务层：按结果类型选择文件名、验证和清理产物。
- 数据访问层：允许成功任务更新实际 `output_file`。
- 文件接口：按真实文件返回正确类型。
- 搜索准备层：增加 PDF 文字提取分支。
- 镜像依赖：加入所需的轻量 PDF 读取依赖，并锁定版本。
- 测试：补充单元、接口、容器和真实地址验证。

## 测试清单

### 自动测试

- 普通 HTML 页面。
- 直接返回 PDF。
- 302/303/307/308 跳转后返回 PDF。
- URL 无 PDF 后缀但内容为 PDF。
- `application/octet-stream` 但内容为 PDF。
- 声明为 PDF但内容是 HTML 登录页。
- 空 PDF、截断 PDF、损坏 PDF。
- 浏览器已登录后保存 PDF。
- 手动处理后复用现有标签页保存 PDF。
- 保存超时和进程异常，确认无临时文件残留。
- PDF 查看、下载、文件列表、重命名显示名、删除。
- HTML 重新归档为 PDF、PDF 重新归档为 HTML。
- 文字型 PDF 的搜索准备。
- 扫描型或无文字 PDF 安全跳过搜索。
- 错误信息中的会话编号和查询令牌脱敏。

### 独立验收

实施者完成自测后，由主智能体独立执行：

1. 审查所有差异，检查是否符合本计划以及项目部署兼容要求。
2. 运行后端全部测试、前端全部测试和现有容器验证脚本。
3. 构建或刷新实际运行镜像，不能只验证宿主机代码。
4. 用示例地址创建真实归档任务。
5. 确认任务成功、结果名为 `.pdf`、文件签名有效、页数为 11。
6. 从 Reader 的查看入口打开 PDF，确认可见内容和翻页正常。
7. 从下载入口下载并再次检查文件完整性。
8. 归档一个普通 HTML 页面并打开结果，确认 SingleFile 行为没有退化。
9. 验证重新归档、删除、搜索和失败清理。

## 旧存档处理

- 不自动批量访问或重做历史记录。
- 已经生成空白 HTML 的任务可以通过“重新归档”按新逻辑修复。
- 如未来需要批量修复，应单独设计显式操作和预览范围，避免重新访问失效或带敏感会话的旧链接。

## 非目标

- 不支持扫描版 PDF 的 OCR。
- 不扩展 Word、Excel、压缩包等任意直链文件。
- 不把 PDF 转换成 HTML。
- 不自动重做全部历史任务。

## 实施与验收结果

- 已于 2026-08-11 完成实施，并由主智能体独立复查。
- 示例地址成功保存为 543,435 字节的 PDF，共 11 页；查看和下载结果一致，没有残留空白 HTML 或临时文件。
- 普通网页归档复测正常，重新归档时可在 HTML 与 PDF 之间正确切换。
- 自动检查全部通过：后端 79 项，前端 16 项，完整镜像构建和容器运行检查通过。
- 独立复查中发现并修正了三项边界问题：加密 PDF 被误判、已打开的 PDF 标签页无法重新捕获、并行的视频检查可能误删 PDF。
- 功能默认包含在应用和镜像中，不需要修改 Compose 配置。
