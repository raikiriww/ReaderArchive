# 搜索升级：实际对照验证

> 历史阶段记录，包含当时的方案、结果和未完成项。当前实现及最终验收以 [CPU 搜索升级](search-cpu-upgrade.md) 和 [发版验收](release-acceptance-20260905.md) 为准。

日期：2026-09-05。只使用 34 篇人工合成文章、31 条固定查询，没有向外部发送用户文章，没有修改用户日常资料库。

## 对照方式

旧版源码来自 Git `fbb3c74ac0228f26bdff5e0e702e7beed2af6793`，导出到临时目录，运行旧版分段、旧版向量入库、旧版查询完整流程。旧库 `reader_semantic_baseline` 与新库 `reader_semantic_eval` 都在独立验证 PostgreSQL 容器内，和用户数据库隔离；API 分别使用本机 38168 与 38167。

两边使用同一批文章、查询、标注、相同本地 MiniLM 模型文件和相同 Python 依赖。新版 `archive-tasks` 已转到新检索，所以没有把这个兼容入口伪称旧基线。关键词对照关闭模型；组合搜索实际运行本地模型，未使用模拟向量。

本组是开发期间的回归资料，不是独立真实用户验收集。速度只反映本机小库，未验证千篇、万篇、后台索引与并发请求下的性能。

## 首轮结果（改进过程记录）

下表使用复核后的同一套标注。数据保存在 `.local_eval/reader-semantic/results/baseline-reviewed`、`hybrid-reviewed`、`keyword-reviewed`；未修订标注的原始结果也保留。

| 指标 | 旧版完整搜索 | 新版组合搜索 | 新版关闭模型 |
| --- | ---: | ---: | ---: |
| 首条结果正确/有用 | 85.2% | 100% | 48.2% |
| 返回前五条中的相关比例 | 55.2% | 66.3% | 46.3% |
| 预期相关文章在前五条的召回 | 92.6% | 100% | 38.9% |
| 4 条原文证据检查 | 2/4 | 4/4 | 4/4 |
| 4 条明确无答案查询误报 | 0/4 | 0/4 | 0/4 |
| 严格整题通过 | 12/31 | 16/31 | 11/31 |
| 请求耗时 p95 | 156.67ms | 94.54ms | 57.50ms |

新版已修复了旧版漏掉长文末段及摘要不包含命中词的问题。原文、短词检索在关闭模型时也能工作。关闭模型的首次短词测试还发现 `Go` 误中 `Google`，随后修复了完整词边界，不能将上表的关键词初测视为最终版本。

**首条变好并不等于整页质量已通过。** 当前模型仍会带出明显无关的内容，比如订阅源整理问题返回 Go 并发笔记、浏览器搜索验证问题返回 Google 历史。这些继续记失败。

实际余弦分数说明仅调统一门槛不能解决全部问题：订阅源整理的正确文章约 0.426，无关 Go 文章约 0.404，而另一篇相关 RSS 文章约 0.393。另一方面，AI 工作周问题的正确中英文文章约 0.801 / 0.705，无关 AI 沟通和漏洞文章也有 0.577 / 0.564。需要独立样本上的相关性校准、候选判断或模型比较，不能用本组问题硬编码规则。

## 最新代码复测

短词边界、预览片段和段落高亮等最终修订落盘后，重新运行同一组 31 问，报告位于 `.local_eval/reader-semantic/results/hybrid-final`。相关性结果与上表的新组合搜索一致：首位有用 100%、前五相关比例 66.3%、召回 100%、证据 4/4、无答案 4/4，严格通过 16/31。该次请求 p95 为 110.48ms，说明前表延迟只是一次本机小样本测量，不是稳定服务承诺。

## 评测本身的修复

- 兼容当前分页返回，同时保留旧数组用于历史对照。
- 明确文章找回要求主目标排第一；主题问题允许任一已标有用答案排第一。
- 同时报告前五相关比例、召回、MRR、NDCG、无答案误报与证据支持，防止“前三有目标”掩盖首条错误和大量无关结果。
- 补充正文短尾、符号 `C++`、短词 `Go` 与相近 `Google` 干扰、更多无答案问题。
- 破坏性灌数必须匹配独立库名、主机、目录、显式许可标记，并拒绝含真实/非评测存档 ID 的数据库。没有对用户真实库执行灌数。
- 当前 19 条独立评测测试通过；shell 语法、compose 配置检查通过。

全部规则及四处有正文证据的漏标修订，见 [评测使用与标注记录](../backend/scripts/semantic-eval-notes.md)。旧、新结果都应用相同修订；原始报告保留。

## 后续验收边界

本轮不能证明已达到设计评估中提出的真实资料质量和大库性能目标。下一批应使用独立真实找回需求、相近但不回答问题的干扰文章与无答案问题，单列校准集和留出集，并验证模型异常、旧存档后台补齐、大库筛选及并发。模型升级需要重新验证输入前缀、切分预算、维度、阈值、速度与镜像默认打包，不应只更换名称。

## 轻量模型候选：E5-small 实际实验

已检查当前 fastembed 的支持表：没有内置 `multilingual-e5-small`，内置的 E5-large 是 1024 维，不能只改名称套进当前 384 维存储。随后下载官方 `intfloat/multilingual-e5-small` 的 ONNX 文件，固定版本 `614241f622f53c4eeff9890bdc4f31cfecc418b3`，用独立评测适配器、独立库 `reader_semantic_e5` 完整索引同一组资料。没有改默认模型，也没有改 38167 上的验收服务。

输入严格使用查询 `query: ` 和正文 `passage: `，包括中文；使用 mean pooling、L2 归一化、384 维和按实际输入计算的 512 token 上限。每个模型输入都有长度与前缀断言。这符合[官方模型用法](https://huggingface.co/intfloat/multilingual-e5-small#usage)。官方也解释该模型余弦通常偏高，因此旧模型阈值不能直接复用。

在**同一开发样本**上探索多个阈值，结果如下。这些不是经过独立留出集校准的生产参数，不能挑最高通过数宣称新模型更好。

| E5 探索阈值 | 首位有用 | 前五相关比例 | 前五召回 | 无答案误报 | 严格通过 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.34 | 92.6% | 33.3% | 94.4% | 4/4 | 2/31 |
| 0.70 | 92.6% | 33.3% | 94.4% | 4/4 | 2/31 |
| 0.80 | 92.6% | 35.6% | 89.5% | 4/4 | 2/31 |
| 0.85 | 92.6% | 65.1% | 85.8% | 1/4 | 10/31 |
| 0.90 | 70.4% | 70.4% | 59.3% | 0/4 | 17/31 |

较高阈值能少给弱结果，但也漏掉更多正确文章。0.90 下严格通过数略高，并不能抵消首位和召回明显下降。当前证据**不支持将 E5-small 直接设为默认**。也不能由一组开发资料推断它普遍差于 MiniLM；不同分段、候选重排及独立数据上的校准仍可能改变结果。

脚本 [e5_candidate_eval.py](../backend/scripts/e5_candidate_eval.py) 只读本地已下载模型；灌数只接受专用空库，不会清空任何现有库。报告保存在 `.local_eval/reader-semantic/results/e5-*`。这组查询直接调用检索，不含 HTTP，且不同阈值下候选数量、缓存状态不同，故没有拿其耗时与前面的 API 时间宣称模型速度优劣。没有部署该试验适配器到应用中。
